\section{Assessment boundary}
This self-assessment covers the delivered local research simulator and its optional LLM parser adapter. It is not a penetration-test certificate, regulatory approval or production assurance. All products and returns are fictional/synthetic. The application cannot connect to a broker or transfer real money. The baseline threat model is untrusted user text or model output entering a trusted, single-user localhost process. A malicious local operator is outside that boundary.

\section{Implemented permission tiers}
\begin{longtable}{p{.18\linewidth}p{.32\linewidth}p{.42\linewidth}}
\toprule Tier & Allowed action & Enforcement\\\midrule
READ & Product comparison and interpretation draft & No parser function receives account or execution tools. Reading cannot propose or approve through service methods.\\
PROPOSE & Generate a reviewed allocation & Requires the trusted application's PROPOSE role. Strict profile and bound schema. Solver abstains on infeasibility or invalid numerical result.\\
APPROVE\_SIM & Approve and execute a simulated rebalance & Requires exact boolean confirmation, a stored proposal, current account revision and unexpired proposal. Execution additionally needs its random approval token.\\
LIVE & None & No live brokerage, payment, wallet or order API exists in the code.\\\bottomrule
\end{longtable}
Role strings are trusted application arguments, not an identity provider. The HTTP controller assigns these roles to its UI workflows after request-token and origin checks. It does not accept a role supplied by the client or model. Within a trusted Python process, an operator can call methods directly; therefore this is capability separation for a simulation, not robust multi-user authorization.

\section{Controls and evidence}
\begin{enumerate}
\item \textbf{Untrusted parser output.} Exact JSON key sets, supported product IDs, finite numerical bounds and size limits. Duplicate keys are rejected. Clarification prevents generation of a draft. Mock attacks including added role fields and NaN fail closed.
\item \textbf{Mandate confirmation.} UI displays interpreted bounds and requires review before a proposal. Schema validity alone cannot detect every semantic misunderstanding. The offline grammar declines unrestricted prose.
\item \textbf{Hard policies.} Long-only budget, concentration, aggregate risk and liquidity limits are compiled independently of the language model. Confirmed client bounds remain hard constraints. Conflicts return NEEDS\_REVISION without weights.
\item \textbf{Proposal integrity.} Application stores a deep copy with a content digest, account revision and five-minute monotonic-clock expiry. Mutating a returned object does not mutate the stored allocation. The digest is an identifier, not a signature or identity proof.
\item \textbf{Explicit simulation approval.} No token appears in parser output or proposal generation. Tokens use the operating-system randomness source, bind to one proposal and become invalid after execution. Reapproval replaces earlier tokens for that proposal. Tests cover missing approval, expiry, stale revision and replay.
\item \textbf{Local web boundary.} Bind only to 127.0.0.1. Exact Host and Origin checks, random POST token, 16 KiB body limit, no-store responses, content-type validation and a nonce-based Content Security Policy. Dynamic text uses textContent. The browser is not permitted to supply the service role.
\item \textbf{Network and secrets.} Optional provider URL is fixed to the OpenAI HTTPS endpoint. Redirects and environment proxies are disabled; request timeout is 12 seconds and response read is capped at 64 KiB. API keys remain in environment variables. No network is used in the baseline numerical workflow.
\item \textbf{Audit and accounting.} JSONL events include sequence, UTC timestamp, previous hash and current SHA-256 hash. The verifier detects modification of retained events and broken order. Execution logs its intended account transition before updating memory; a write error stops execution. The simulator records fee, NAV, notional changes and revision.
\end{enumerate}

\section{Verification status}
The included unittest run passes 51 test methods, including 40 randomized feasibility instances inside one method and end-to-end HTTP execution. The separate evidence session asserts seven expected outcomes and verifies a nine-event chain. Solver feasibility and objective reconstruction residuals are included in the actual JSON outputs. This evidence comes from a local simulated account, not a competition-hosted sandbox. The LLM adapter was tested using injected responses and failure cases; the live API was not exercised. Docker was not built, no external penetration test was performed, and a full browser-interaction automation run is not claimed.

\section{Release decision}
Suitable for a clearly labeled, single-user competition demonstration with synthetic inputs. Not suitable for real-money execution or public multi-user deployment. The team should review all claims, publish the actual code repository, check competition submission rules and keep any registration/passport documents separate from source code.
